# v0.4.0 — Write Filesystem Tools Design

    Status: implementation in progress.

    This is the release where Muru's confirmation engine fires for real. Three
    write tools land, each at a different risk tier, so the user experiences
    the full Tier 2 / 3 / 4 spectrum we built in v0.3.0.

    ## Tools and tiers

    | Tool | Target state | Tier | UX |
    |---|---|---|---|
    | `write_file` (new file) | Target does not exist | 2 (Medium) | yellow panel, y/n |
    | `write_file` (overwrite) | Target exists | 3 (High) | orange panel, type "yes" |
    | `move_file` | Source exists, dest may or may not | 3 (High) | orange panel, type "yes" |
    | `delete_file` | Target exists | 4 (Critical) | red panel, 5s cooldown, type tool name |

    Rationale: tier reflects reversibility cost. Creating a new file is
    cheap to undo (just delete it). Overwriting destroys the prior content.
    Moving makes the source disappear. Deleting requires undo plumbing to
    reverse, which v0.4.0 does not yet have.

    Because `write_file`'s tier depends on target existence, the tool itself
    reports its tier at planning time after a stat() check. The Tool wrapper
    will need to support tier-as-function (callable) in addition to tier-as-
    constant. For v0.4.0 we take a simpler path: `write_file` declares Tier 3
    statically (the higher of its two possible tiers), so users always get the
    stricter UX. Smarter dynamic tiering is a v0.5.0+ refinement.

    ## Atomic write strategy

    Naive `write_file` opens the target and writes bytes. If anything fails
    mid-write (disk full, signal, OS panic), the target is left half-written
    and the prior content is gone. Unacceptable for a tool that runs on
    user files.

    Strategy: write to a sibling temp file `<target>.muru-tmp-<pid>`, then
    atomically rename into place with `os.replace()`. POSIX guarantees
    `rename` is atomic within the same filesystem.

```python
    tmp = target.with_name(target.name + f".muru-tmp-{os.getpid()}")
    try:
        tmp.write_text(content, encoding="utf-8")
        os.replace(tmp, target)
    except Exception:
        if tmp.exists():
            tmp.unlink()
        raise
```

    `move_file` and `delete_file` use stdlib functions (`shutil.move`,
    `Path.unlink`) which are already as safe as possible.

    ## delete_file scope

    v0.4.0 intentionally restricts delete to the safest possible shape:
    - One target path per call
    - Files only, not directories (directory delete is qualitatively
      different — affects many files at once, recursion semantics matter)
    - No glob expansion (`*.tmp` is not a valid path)
    - Sandboxed to user home via `safe_resolve()` like all other tools

    Recursive directory deletion and bulk delete-by-glob are deferred to
    v0.4.1 or later, with extra ceremony (probably preview-list-then-confirm).

    ## Undo metadata

    v0.4.0 does not implement undo (that is v0.5.0's job), but write tools
    emit enough metadata for v0.5.0's audit log to reconstruct undo
    operations:

    | Tool | Metadata |
    |---|---|
    | `write_file` (new) | tool_name, path, size_bytes, created=True |
    | `write_file` (overwrite) | tool_name, path, size_bytes, previous_content (if ≤10MB), previous_size_bytes |
    | `move_file` | tool_name, source_path, dest_path |
    | `delete_file` | tool_name, path, size_bytes, deleted_content (if ≤10MB) |

    Why the 10MB cap on captured content: a large delete or overwrite should
    not silently load gigabytes into RAM. v0.5.0 will integrate with a real
    trash directory for large files. For now, the result includes
    `deleted_content=None` and a note that the operation is not undoable.

    ## Sandbox rule

    All v0.4.0 tools use `safe_resolve()` from `muru.tools.filesystem._safety`,
    same as v0.2.0's read tools. This means:
    - Paths must resolve inside the user's home directory
    - Symlinks that point outside the sandbox are rejected
    - `..` traversal that escapes the sandbox is rejected
    - Paths starting with `~/` are expanded; `/` paths must already be in `~`

    No v0.4.0 tool can touch anything outside the user's home directory,
    even if the planner tries to call it with `/etc/passwd`.

    ## Error handling

    All tools follow the v0.2.0 pattern:
    - Return `success=False, message=<reason>` for predictable failures
      (path not found, permission denied, path outside sandbox)
    - Raise `ToolExecutionError` for unexpected failures (OS errors,
      programming bugs) — the orchestrator catches these and asks the
      LLM to explain to the user

    Predictable failures are not exceptions because the LLM should be
    able to read the message and rephrase the situation to the user
    without an error-handling code path.
